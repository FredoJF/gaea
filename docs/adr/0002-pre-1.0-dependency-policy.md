# ADR-0002: Pre-1.0 Dependency Policy

**Status**: Accepted — constitution amended to v1.1.0 on 2026-09-16

**Date**: 2026-09-16

**Supersedes**: the deviation recorded in [ADR-0001](0001-language-runtime-and-datastore.md)

## Context

ADR-0001 recorded a direct conflict with the constitution. Principle III as ratified required every
dependency to be on a stable `>= 1.0` release line and stated that pre-1.0 packages MUST be
rejected. Measured on 2026-09-16, the Rust ecosystem this project depends on does not satisfy that:

| Crate | Version | Line | Last release |
|---|---|---|---|
| twilight-* | 0.17.1 | pre-1.0 | 2025-12-13 |
| serenity (alternative) | 0.12.5 | pre-1.0 | 2025-12-20 |
| axum | 0.8.9 | pre-1.0 | 2026-04-14 |
| sqlx | 0.9.0 | pre-1.0 | 2026-05-21 |
| askama | 0.16.1 | pre-1.0 | 2026-09-04 |
| tracing | 0.1.44 | pre-1.0 | 2025-12-18 |

`tracing` alone has 851 million downloads and is the de facto standard for structured logging in
Rust. A rule that rejects it is not protecting the project from anything.

The rule was aimed at a real risk — depending on software that churns its API or is abandoned — but
it used a version number as a proxy for that risk. In the Rust ecosystem that proxy does not hold:
0.x lines are routinely production-grade and maintained for years, while a 1.0 badge guarantees
nothing about maintenance.

## Decision

Principle III is amended (constitution v1.0.0 → v1.1.0, MINOR: existing guidance materially
expanded). The `>= 1.0` requirement becomes a preference that breaks ties; a pre-1.0 dependency may
be adopted only when **all six** of the following hold and the adopting ADR records each:

1. No `>= 1.0` alternative of comparable engineering merit exists.
2. The upstream repository is not archived or deprecated, and shows commit activity within 90 days.
3. The license permits forking.
4. The dependency is isolated behind an internal boundary owned by this project — no type it defines
   appears in domain logic, so it can be replaced or forked without touching that logic.
5. A named maintainer on this project owns tracking it.
6. Its release cadence is measured and recorded, not assumed.

The prohibition on *unmaintained* packages is kept and given a testable definition: archived,
explicitly deprecated, or no commit in twelve months. Infrequent releases alone are not
disqualifying where development is demonstrably ongoing, but the gap must be recorded and condition
(4) applies.

## Alternatives Considered

**Build the Discord client in-house.** Principle III already contemplated this. Gaea uses a narrow
slice of the Discord API, so it is genuinely feasible. Rejected because it moves the permanent
burden of tracking a continuously changing platform API onto this project, in exchange for avoiding
a dependency whose repository is demonstrably active. It also would not have solved the same problem
for Axum, SQLx, Askama, or tracing.

**Record a standing deviation.** Rejected: a MUST carrying a permanent exception erodes the document
it appears in, and the exception would have had to be repeated for every layer of the web stack.

**Replace the version rule with a purely behavioural maturity test.** Attractive, and closest to what
the principle is actually trying to express. Rejected as this amendment's scope because it is a
larger change (arguably MAJOR) and the conditional carve-out above captures most of its value while
keeping `>= 1.0` as a meaningful tie-breaker.

## Consequences

- Twilight, Axum, SQLx, Askama, and tracing become adoptable, each subject to conditions 1–6 being
  recorded in its own ADR.
- **Condition (4) is now binding architecture, not advice.** Every pre-1.0 dependency must sit behind
  a project-owned boundary. For Twilight this means a trait defining only the operations Gaea needs;
  no Twilight type may appear in domain logic, in the dashboard, or in the data layer.
- Condition (2) must be re-checked as part of the dependency review that Principle IV already
  requires in CI, not only at adoption time.
- Condition (5) makes ownership explicit. With a single maintainer this is a formality today; it
  stops being one as soon as anyone else contributes.
- The amendment is not retroactive by accident: it is being adopted before any implementation code
  exists, so nothing needs migrating.
